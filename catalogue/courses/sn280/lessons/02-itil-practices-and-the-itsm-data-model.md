## Why vocabulary is a configuration problem

Every ITSM implementation begins with an argument that looks like a semantic quibble and is actually a data-model decision. The service desk manager says "we get about four hundred incidents a week." You look at the queue and half of them are password resets and new-laptop requests. Those are not incidents. They are requests. If they are recorded as incidents, then every metric the customer cares about — mean time to restore, first-call resolution, incident volume trend — is measuring a blend of two processes with different goals, and no amount of reporting configuration will separate them afterward.

ITIL is the vocabulary that resolves this. In this course you are not studying for an ITIL certification and you do not need to recite the service value chain. What you need is the subset of ITIL that the ServiceNow tables actually encode, because the platform's out-of-box process applications are built as if those definitions were true. When you know the definitions, the table you should be using is usually obvious. When you do not, you end up building a custom field to record something the platform already models, and that is the first step toward an implementation that cannot be upgraded.

The four practices this course configures are defined as follows, in the shape the platform assumes:

An **incident** is an unplanned interruption to a service, or a reduction in its quality. The goal of incident management is to restore normal service as quickly as possible. Speed beats elegance. A workaround that gets the user working counts as success.

A **problem** is the cause, or potential cause, of one or more incidents. The goal of problem management is to reduce the likelihood and impact of incidents, by finding root cause and by publishing known errors and workarounds. Problem management is deliberately slower than incident management, and it is allowed to be. The two run on different clocks.

A **change** is the addition, modification, or removal of anything that could have a direct or indirect effect on services. The goal of change management — change enablement, in current ITIL wording — is to maximize the number of successful changes by assessing risk and authorizing work properly. Change is the only one of the four practices whose primary output is an approval decision.

A **service request** is a request from a user for something normal and pre-defined: access, information, a standard piece of equipment, a routine task. The goal of request fulfilment is predictable delivery of standard services. Requests are planned work. Incidents are not.

The practical test you will apply on every implementation: *was something broken?* If yes, it is an incident. *Is someone asking for something the catalog already offers?* Request. *Are we trying to stop a class of failure recurring?* Problem. *Are we altering the environment?* Change.

## The task table and why everything inherits from it

ServiceNow does not implement these four practices as four unrelated applications. It implements them as four extensions of one base table, `task`. This is the single most important structural fact in ITSM, and almost every configuration decision in the rest of this course refers back to it.

The `task` table holds the fields that any unit of work has: `number`, `short_description`, `description`, `state`, `assigned_to`, `assignment_group`, `opened_at`, `closed_at`, `priority`, `impact`, `urgency`, `approval`, `sys_created_by`, and the `work_notes` / `comments` journal fields. It also carries the `cmdb_ci` reference and the `parent` reference that lets tasks nest.

Each process table extends `task` and adds only what is specific to it:

```text
task
├── incident              (caller_id, incident_state, problem_id, rfc, cause_code…)
├── problem               (problem_state, known_error, workaround, cause_notes…)
│   └── problem_task      (problem_task_type: RCA, investigation, general)
├── change_request        (type, risk, category, start_date, end_date, cab_required…)
│   └── change_task       (change_task_type: planning, implementation, testing, review)
├── sc_req_item           (cat_item, request, stage, quantity, price…)
│   └── sc_task           (the fulfilment work generated by a requested item)
└── sc_request            (requested_for, stage, approval, request_state)
```

![Task table inheritance across the ITSM process tables, showing incident, problem, change request, and requested item as extensions of a common task base](./img/itsm-task-table-inheritance.png)

Three consequences follow, and they are worth internalizing now.

**A field added to `task` appears on every process table below it.** That is occasionally what you want — a single "business unit" field that must be reported across all work types — and it is much more often a mistake, because you have just widened the schema of six tables to satisfy one requirement. The default answer is to add the field to the specific table.

**Anything that queries `task` sees all of them.** A business rule with a table of `task` and `Advanced` scripting runs on incidents, changes, requested items, and change tasks alike. So does a UI policy, so does an assignment rule, and so does an SLA definition scoped to `task`. This is a powerful lever and an easy way to cause a performance incident. Be deliberate.

**Reporting joins are already available.** Because `sc_task`, `change_task`, and `problem_task` all extend `task`, a manager's "show me everything assigned to my group" list is one query against `task` filtered by `assignment_group`, not five reports stitched together.

## The reference tables ITSM leans on

The process tables would be useless without the reference data they point at. Four matter most.

`sys_user` holds people. On an incident, `caller_id` points here — the person affected — while `assigned_to` points here as well, the person doing the work. Confusing the two is a classic implementation error that ruins "who reports the most incidents" reporting forever.

`sys_user_group` holds groups. `assignment_group` points here. Groups have a `type`, and the type is how the platform distinguishes an approval group from a fulfilment group from a change advisory board. Group membership lives in `sys_user_grmember`, which is a many-to-many table, not a field on the user.

`cmdb_ci` and its class hierarchy hold configuration items — the services, applications, servers, and devices that incidents affect and changes alter. The `cmdb_ci` field on `task` is the join that makes "which service is currently degraded" answerable. Lesson 10 covers how that data gets there and stays correct; here you only need to know it is a reference, not a text field, and that the quality of every service-level report downstream depends on it being populated.

`cmdb_ci_service` — business services — is the class that matters most for ITSM reporting, because executives ask about services, not servers.

## Mapping a customer's practices onto the model

Discovery for an ITSM engagement is not a list of feature requests. It is a mapping exercise: you take the practices the customer runs today, however informally, and place them on the model above. Do this as a workshop, and produce a written artifact.

A worked example. A mid-sized organization tells you the following:

> "The helpdesk logs tickets. If it's a big outage the on-call manager declares a Sev-1 and we run a bridge call. Every quarter we do an outage review and write up what happened. Anything touching production needs sign-off from the infrastructure lead, except for patching, which we just do on the second Tuesday. New starters get a form emailed to IT."

Mapped:

| What they said | Practice | Table | Note |
| --- | --- | --- | --- |
| Helpdesk logs tickets | Incident, mixed with request | `incident` and `sc_req_item` | Must be split; the ticket queue is currently both |
| Sev-1 with a bridge call | Major incident | `incident` with major incident handling | A state and a process overlay, not a new table |
| Quarterly outage review | Problem, run reactively | `problem` and `problem_task` | Currently a document, not a record |
| Sign-off from infrastructure lead | Normal change | `change_request` type `normal` | One approver, not a full CAB |
| Patching on the second Tuesday | Standard change | `change_request` type `standard` | Pre-approved, from a change template |
| New starter form emailed to IT | Request fulfilment | Catalog item producing `sc_req_item` and `sc_task` | Email is the current channel; the catalog replaces it |

Notice what this mapping does. It converts vague statements into table-level decisions, and it exposes the two real project risks — the ticket queue conflates incidents and requests, and problem management exists only as a document. Both are now visible to the customer before you have configured anything.

## Using ITIL and Agile without over-engineering the delivery

Two failure modes bracket this work. The first is the customer who wants every ITIL practice modeled at maximum fidelity from day one: five change types, a four-tier CAB, a formal known-error database, and continual-improvement records — before a single incident has been logged in the new system. The second is the customer who wants "just incidents, keep it simple," and then discovers in month three that everything is an incident and nothing is measurable.

The delivery answer is iterative. Structure ITSM implementations as sprints against a prioritized backlog, where each sprint delivers one usable slice of a practice and gets demonstrated to real process owners. A reasonable first three sprints:

1. Incident: intake, categorization, priority, assignment, resolution. Demo it with the service desk actually logging a ticket.
2. Request: three catalog items covering the highest-volume standard requests, with fulfilment tasks. Demo it with a real requester.
3. Change: standard and normal types, one approval path, a change schedule. Demo it with a real change going through.

Problem, SLAs, and automation follow, once there is real data for them to act on. This is Agile delivery applied to a process implementation: the increment is a working process, the demo audience is the process owner, and the backlog is written in the customer's ITIL vocabulary so acceptance is not ambiguous. Keep a definition of done that includes "the process owner has run one real record through it," not "the configuration is saved."

The complementary discipline is scope. Every practice you add multiplies the states, roles, notifications, and reports that have to be maintained. When a customer asks for a practice, ask who will operate it and what decision the data will drive. If neither has an answer, the practice belongs in a later phase.

## Practice

Work in a personal developer instance.

1. Open the table definitions for `incident`, `problem`, `change_request`, and `sc_req_item`. For each, list which fields are inherited from `task` and which are defined on the table itself. Write down two fields per table that you were surprised to find are inherited.

2. Create one record on each of the four process tables using the out-of-box forms, filling only the mandatory fields. Then run a single list query against the `task` table filtered to records you created today, and confirm all four appear in it.

3. Take the customer statement below and produce the mapping table shown in this lesson — the customer's words, the ITIL practice, the ServiceNow table, and a note flagging any risk or ambiguity:

   > "Users email the shared IT inbox. Anything urgent gets escalated to the platform team's chat channel. We track recurring issues in a spreadsheet. Server rebuilds need an email approval from the ops manager. Contractors request VPN access by opening a ticket titled 'VPN'."

4. For each row of your mapping, write one sentence naming the specific risk of leaving that item where it currently lives. At least two rows should identify a measurement problem, not just an efficiency problem.

5. Sequence the mapping into three delivery sprints. For each sprint, state the demo you would run and the definition of done, in the customer's vocabulary rather than in platform terms.
