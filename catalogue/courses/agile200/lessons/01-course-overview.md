## Description

This course is your capstone. Everything you have learned so far about agile teams, version control, and writing code comes together here, but the lens you will use for the next three weeks is quality assurance. You and your team will scope a real project, build it in short sprints, and ship it — but the artifacts a reviewer will actually grade are the ones a QA engineer produces: a working test environment, a written test strategy, an automated test suite that survives the code changing underneath it, a defect database, and a release you can stand behind with evidence.

You will spend the first part of the course building the scaffolding a QA engineer needs before a single line of test code gets written: a scoped project with an agreed definition of done, a truthful sprint board, a representative test environment, and a strategy that matches the project's real risk and timeline. From there you move into the work itself — writing and maintaining automated tests, running a defect database a team can actually use, and diagnosing problems the way they show up in the real world, from an actual user or stakeholder rather than a ticket you wrote yourself. The course closes with verifying a release, handing it off with documentation someone else could follow, presenting the work, and running a retrospective.

The final three weeks are a live capstone sprint that re-runs this entire sequence for real, under time pressure, on a codebase that keeps changing. That is deliberate — maintaining a test suite against a moving target and fielding a real complaint from a real user are skills that only show up when the project is real and the clock is running.

## Objectives

- Scope a capstone project and write a definition of done the team agrees on
- Run a sprint board in project management software and keep it truthful
- Stand up a test environment that represents how the project will really run
- Write a test strategy that matches the project's risk and timeline
- Write and maintain automated test scripts as the code changes
- Keep a defect database a team can actually use
- Work with users and stakeholders to diagnose reported problems
- Verify a release and hand it over with accurate documentation
- Present finished work and run a retrospective
