## What Data Element Validation checks

Data Element Validation (DEV) is the process of comparing what was reported for a participant against the source documentation in the file. A sample of records is pulled, and for each selected data element a reviewer looks for documentation that supports the value in the system. If the document is missing, or it says something different from the system, the element fails.

DEV is not a re-check of whether you made a good decision. It checks whether the record matches the evidence. That is why a participant who was truly eligible and truly attended training can still fail validation. The acceptable source documents for each data element are set in state guidance. Check the current Acceptable Documentation List and validation directive from EDD before you decide that a given document is enough.

## Eligibility is not validation

CCC's catalog cites San Joaquin WorkNet's Directive 23-04, which lists confusing eligibility with validation among the repeated staff errors. The two are related but different:

| | Eligibility | Validation |
| --- | --- | --- |
| Question asked | Can this person be served in this program? | Does the file prove what the system reports? |
| When | At enrollment | After the fact, on sampled records |
| Covers | Eligibility criteria | Many reported elements, including dates, services, and outcomes, not only eligibility |
| A file can... | Show eligibility clearly | Still fail if, for example, an activity date has no matching source document |

A complete eligibility packet does not protect the rest of the record.

## The recurring errors

These are the patterns to look for. Most of them trace back to the habits in the previous lessons.

1. **Dates that don't match the source.** Begin or end dates taken from vouchers, schedules, or data-entry dates instead of attendance or completion records.
2. **Late codes.** Activities entered long after the service, often with dates that are guesses. CCC's catalog notes late codes among the errors in Directive 23-04.
3. **Opinion instead of evidence in notes.** Notes that characterize the participant but don't document what service occurred.
4. **Activities with no supporting note or document.** A code is in the system but nothing in the file explains it.
5. **Notes with no matching activity.** A service is described in a note but never recorded, so it never counted.
6. **Plans that don't support the service.** An IEP or ISS with no assessment evidence for the training or OJT chosen.
7. **Missing or wrong source documents.** A document is present but isn't one the state accepts for that element, or the values on it differ from the system (a different date, name spelling, or credential).
8. **Self-attestation used where it isn't allowed.** Whether self-attestation is acceptable depends on the element; check the current documentation list.

## A quick self-audit

Before you consider a file complete, pick three elements and trace each one from the system value to the document.

| Element | System value | Source document in file | Match? |
| --- | --- | --- | --- |
| Training begin date | [date] | Provider attendance roster | Yes / No |
| Credential attained | [credential] | Certificate copy | Yes / No |
| Career counseling service | [date] | Case note dated [date] | Yes / No |

Any "No" is a fix to make now, with a case note explaining the correction.

## Discussion prompt

Which of the eight errors do you think shows up most in your own office? Why?

## Practice

Review this fictional record summary and list every error you can find, naming which of the eight patterns it fits.

- Training activity begin date: February 20 (voucher issue date). Roster shows first attendance March 10.
- Case note dated May 2: "Participant seems to be doing fine."
- Supportive service activity recorded March 5. No note or receipt in file.
- Credential recorded as "Certified Medical Assistant." Certificate in file reads "Clinical Medical Assistant."
- IEP lists goal "healthcare job" with no assessment results referenced.
