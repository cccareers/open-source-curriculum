## Reading is the reverse of writing, and harder

Generation starts from clean structured data and produces prose. Extraction starts from prose — often scanned, often badly formatted, often from a vendor whose template changed last month — and must produce clean structured data. The output feeds a workflow that will act on it, which means a wrong field is not a typo, it is a wrong payment or a misrouted claim.

The pipeline:

```text
capture -> text acquisition -> chunk -> extract (schema-bound) -> validate
        -> confidence route -> write fields -> summarize (separate call)
```

Two design commitments make the difference between a demo and something you can run on 900 documents a month. **Define the target schema before you write a prompt** — extraction with no schema produces fields that shift shape between documents and break everything downstream. And **treat every extracted field as a claim with evidence and a confidence**, not as a fact. The claim gets checked; only checked claims get written.

## Capture and text acquisition

Documents arrive as email attachments, uploads, shared-drive drops, or a partner API. Whatever the source, the first step stores the original file untouched with an ID, the source, and the receipt time — the same "keep the raw payload" rule as data ingest, and for the same reason.

Then get text. There are two very different cases, and confusing them causes most extraction mysteries:

**Native text.** A PDF generated by software carries a real text layer. Extraction is exact, but reading order can be scrambled and tables often come out as interleaved columns. Always inspect the extracted text of a sample before building a prompt around it; what looks like a neat table in the viewer may arrive as three lines of column headers followed by forty numbers.

**Scanned images.** No text layer, so optical character recognition produces one. OCR introduces a characteristic error set: `0`/`O`, `1`/`l`/`I`, `5`/`S`, `rn`/`m`, dropped decimal points, and merged or split columns in tables. These errors are not random noise — they cluster in exactly the numeric fields you most need to be right.

Detect which case you are in programmatically: if the extracted text layer is empty or under a small character threshold, route to OCR. Record which path was taken on the record, because it changes how much you should trust a numeric field, and it is the first thing you will want to know when a value is wrong.

Two more capture-time facts worth storing: page count and whether the document has multiple documents inside it. Batch scans regularly contain three invoices in one PDF. If your pipeline assumes one document per file, it will extract the first and silently ignore the rest — an invisible failure, which is the worst kind.

## Define the schema first

Write the target schema as a contract with types, requiredness, and null policy, before any prompting.

```json
{
  "document_type": "invoice",
  "fields": {
    "vendor_name":    {"type": "string",  "required": true,  "null_allowed": false},
    "vendor_tax_id":  {"type": "string",  "required": false, "null_allowed": true},
    "invoice_number": {"type": "string",  "required": true,  "null_allowed": false},
    "invoice_date":   {"type": "date",    "required": true,  "format": "YYYY-MM-DD"},
    "due_date":       {"type": "date",    "required": false, "null_allowed": true},
    "po_number":      {"type": "string",  "required": false, "null_allowed": true},
    "currency":       {"type": "enum",    "values": ["USD", "CAD", "EUR", "GBP"]},
    "subtotal":       {"type": "decimal", "required": true},
    "tax":            {"type": "decimal", "required": false, "default": 0},
    "total":          {"type": "decimal", "required": true},
    "line_items":     {"type": "array",   "item": {
        "description": "string", "quantity": "decimal", "unit_price": "decimal", "amount": "decimal"
    }}
  }
}
```

Every field in that schema exists because a downstream step needs it. If you cannot name the step that consumes a field, remove it — each extra field is another opportunity to be wrong and another thing a reviewer has to check.

## The extraction prompt

Three requirements distinguish a production extraction prompt from a naive one: **null over guess**, **evidence per field**, and **confidence per field**.

```text
You extract structured data from a business document. You do not interpret, infer,
or complete information. You transcribe what the document states.

Return only this JSON object:
{
  "fields": {
    "<field_name>": {
      "value": <typed value or null>,
      "evidence": "<verbatim text from the document that contains this value, or null>",
      "page": <page number or null>,
      "confidence": <0.0-1.0>
    }
  },
  "document_notes": {
    "appears_to_be": "<one of: invoice, credit_note, statement, other>",
    "contains_multiple_documents": true|false,
    "legibility": "<one of: clean, degraded, poor>"
  }
}

Rules:
- If the document does not state a value, set value to null and confidence to 0.
  Never infer a value from context, never carry a value over from another field,
  never compute a value that is not printed.
- evidence must be copied character-for-character from the document text. If you
  cannot quote it, the value must be null.
- Dates: output YYYY-MM-DD. If the printed format is ambiguous (for example 03/04/2026)
  and the document contains no other date that resolves the convention, set value to
  null and explain in evidence which formats were possible.
- Amounts: digits and a decimal point only. Strip currency symbols and thousands
  separators. Do not round. Do not convert currency.
- confidence reflects how clearly the document states the value: 1.0 for a clearly
  printed labeled field, lower for a value you had to locate by position or that is
  hard to read.
- Extract every line item you can see. Do not summarize or merge line items.

Target schema:
{{schema_json}}

Document text:
{{document_text}}
```

The evidence requirement is the highest-value line in the whole prompt. It gives a human reviewer somewhere to look, it makes the model's failures visible ("evidence does not contain the value it claims to support" is a checkable assertion), and it markedly reduces confident invention because the model has to point at something.

The ambiguous-date rule is worth the space it takes. `03/04/2026` is genuinely undecidable and a model will pick one convention cheerfully. Returning null and routing to a human is correct behaviour; guessing right 60% of the time on payment due dates is not.

## Validation: check the claims

Model output is untrusted input. Run it through the same discipline as any other external payload, in four layers.

**Structural.** Does it parse? Are all schema keys present? Are types right? Is `currency` in the allowed enum? A structural failure gets one retry with the parse error appended, then quarantine.

**Evidence consistency.** For each non-null field, does the `evidence` string actually appear in the document text, and does the normalized `value` appear within the evidence? This catches fabricated evidence and value-evidence mismatch, and it is pure string work — no model call needed.

**Arithmetic.** `sum(line_items.amount)` must equal `subtotal` within a small tolerance; `subtotal + tax` must equal `total`. This single check catches most OCR digit errors, because a mangled digit almost always breaks the sum. When the arithmetic fails, you know something is wrong even if you do not know which field.

**Business lookups.** Does `vendor_name` match a known vendor, exactly or closely? Does `po_number` exist in the finance system, and does its amount match within tolerance? Is `invoice_number` already recorded for this vendor — a duplicate-invoice check that pays for the whole project on its own? Is `invoice_date` in a plausible range, not two years old and not in the future?

Every failed check is recorded on the record with the rule name, so the reviewer sees "line items do not sum to subtotal (2,431.00 vs 2,437.00)" rather than a generic warning.

## Confidence routing

Now combine model confidence with your own checks into a routing decision. Do not use the model's self-reported confidence alone — it is a useful signal and a poor authority.

A workable composite: a field is **trusted** when its model confidence is at or above your floor, its evidence check passed, and every business rule touching it passed. Then route the document:

| condition | route | who acts |
| --- | --- | --- |
| all required fields trusted, arithmetic balances, PO matched | `auto_post` | nobody, sampled at 5% |
| all required fields present, arithmetic balances, no PO match | `light_review` | AP clerk confirms PO |
| any required field null or untrusted, or arithmetic fails | `full_review` | AP clerk, field-by-field |
| legibility `poor`, or `contains_multiple_documents` true, or type not invoice | `exception` | AP lead |

Set the floor empirically, not by taste. Label 50 documents by hand, run extraction, and plot accuracy against reported confidence. If everything above 0.9 is right and the 0.7-0.9 band is 85% right, your floor sits at 0.9 and the band below it is your review queue. Re-measure whenever a vendor template changes.

The reviewer screen matters as much as the model. Show the document page beside the extracted fields, highlight the evidence span for each field, put the failed checks at the top, and default the cursor into the first untrusted field. Capture corrections — a corrected field is a labeled example, and a hundred of them tell you exactly where your prompt or your schema is wrong.

## Summarization as a separate job

Summarization and extraction are different tasks and belong in different calls. Extraction wants zero creativity; summarization wants controlled compression. Combining them degrades both and makes failures hard to attribute.

```text
You summarize a business document for an operations reader who will not open the file.

Length: 60-90 words, one paragraph, plain prose.

Rules:
- Use only information present in the document. Introduce no facts, names, dates, or
  amounts that do not appear in it.
- State what the document is, who it is from, what it asks for or reports, and any
  deadline or action it names.
- If the document states an obligation or a deadline, that must appear in your summary.
- Do not evaluate, advise, or recommend. Do not speculate about intent.
- If the text is too degraded to summarize reliably, output exactly:
  UNRELIABLE: <one sentence saying why>.

Document text:
{{document_text}}
```

For long documents, summarize in two passes: chunk on structural boundaries (sections, pages) rather than fixed character counts, summarize each chunk with its page range, then summarize the chunk summaries into the final text. Keep the page ranges — a summary sentence a reader cannot trace back to a page is a summary they cannot act on.

Chunking also matters for extraction on long documents. Send the model the pages likely to contain the fields (an invoice's totals are on the last page; a contract's term is near the front), rather than 60 pages of text in which the relevant line is a needle. If you must scan the whole document, extract per chunk and merge, taking the highest-confidence non-null value per field and flagging any field where two chunks disagree — a disagreement is a signal, not noise to be averaged away.

## Measuring accuracy

Extraction is the one part of this course where you can and must put a number on quality.

Build a **gold set**: 40 to 60 real documents spanning your actual mix of vendors, formats, and scan quality, with every field keyed by hand. Include the ugly ones. A gold set of clean documents proves nothing.

Report **field-level accuracy**, not document-level. Overall document accuracy of 80% is uninformative; "invoice_number 99%, total 97%, due_date 74%" tells you exactly where to spend your next hour. Track three rates per field: correct, wrong, and correctly-null. Wrong is the number that matters — a null routed to a human is a cost, a wrong value written silently is a loss.

Then track two operational rates in production: **review rate** (share of documents needing a human) and **escape rate** (share of auto-posted documents later found wrong, from your 5% sample and from downstream complaints). A rising review rate usually means a vendor changed a template. A rising escape rate means your confidence floor is too low, and it is the only one of the two that is an emergency.

## Practice

Build an extraction pipeline over a real document class you can gather at least 40 examples of — invoices, purchase orders, timesheets, certificates, or resumes. Use public samples or redact real ones.

1. **Assemble the corpus.** At least 40 documents, deliberately including at least 8 scans or photos, 2 multi-document files, 2 with ambiguous dates, and 3 from a differently-formatted source. Key every field by hand into a gold set. Budget real time for this; it is the exercise.
2. **Write the schema** with types, requiredness, null policy, and a named downstream consumer for every field.
3. **Build capture and text acquisition**, including the empty-text-layer detection that routes to OCR, and store the path taken on the record.
4. **Build the extraction step** with the value/evidence/page/confidence structure and the null-over-guess rule.
5. **Build all four validation layers**: structural, evidence-consistency (evidence appears in the document text and contains the value), arithmetic reconciliation, and at least one business lookup such as a duplicate check.
6. **Calibrate the confidence floor.** Plot per-field accuracy against reported confidence across your gold set. Choose a floor, state the accuracy you get above it, and state the review rate that floor implies. A floor with no measurement behind it does not count.
7. **Implement the routing table** with at least three tiers including an exception tier for poor legibility and multi-document files.
8. **Add summarization** as a separate call with the unreliable-output escape, and run it on your three longest documents using structural chunking with page ranges.
9. **Report field-level accuracy** for every field as correct / wrong / correctly-null, and name the single worst field. Then make one targeted change — to the prompt, the schema, or the chunking — and re-measure that field. Report both numbers.
