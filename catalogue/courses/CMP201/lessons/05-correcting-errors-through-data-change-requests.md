## Fixing an error is part of the record

When your self-audit finds an error, the fix has to be as defensible as the original entry. A reviewer who sees a changed value with no explanation, or a document dated after the fact with no note, has a new reason to question the file. The aim is a correction that shows what was wrong, what the evidence says, and who changed it, when.

## Two kinds of correction

Not every fix needs the same path.

| Situation | Typical path |
| --- | --- |
| Record is open and staff can still edit the field | Correct it directly, then write a case note explaining the change and the source document |
| Record is locked, closed, or already reported, so staff cannot edit it | Submit a **Data Change Request** through your area's process |
| Document is missing entirely | Try to obtain an acceptable document; if one cannot be obtained, do not change the data to make it "fit" |

Which fields lock, and when, depends on the system and the reporting calendar. Confirm with your MIS administrator and the current EDD guidance on data changes. Your board's local policy sets who may submit and approve a request.

## Timing: before the annual report

A correction made after data is reported may not change what was reported, and one made during the DEV document window looks like a scramble. That is why the course objective stresses correcting errors *before the annual report*. Build a cutoff into your monthly routine: any fix that needs a Data Change Request goes in that month, not "when we get to it." Check the current EDD calendar for the dates that apply in your program year.

## What a good request contains

Whatever form your area uses, a request a reviewer can follow includes:

1. Participant identifier and program.
2. The element, the current (wrong) value, and the correct value.
3. The source document that supports the correct value, with its date.
4. Why the error happened, in one sentence.
5. Who prepared it and who approved it, with dates.

Then add a case note in the participant's file that says the same thing in plain language.

### Worked example

> 03/14 Self-audit found training begin date entered as 01/20 (voucher issue date). Provider attendance roster in file shows first attendance 02/03. Record is closed; submitted Data Change Request to MIS admin to correct begin date to 02/03. Roster attached. — J. Okafor, Case Manager

## Lines you never cross

- Never create or backdate a document to cover a missing one.
- Never change a value to match a document that doesn't belong to the participant or the right time period.
- Never let a fix happen without a note. An unexplained change is a new finding.

If no acceptable document exists, record that honestly and tell your supervisor. A failed element is a training problem; a fabricated one is an integrity problem.

## Practice

For each fictional case below, decide the path (direct edit plus note, Data Change Request, or obtain document) and write the case note or request summary.

1. Open record. System shows highest grade completed "high school diploma." Transcript in file shows an equivalency certificate.
2. Closed record, already reported. Credential recorded as "Certified Medical Assistant"; certificate reads "Clinical Medical Assistant."
3. Open record. Dislocated worker status entered, but no layoff letter or UI record in file.
