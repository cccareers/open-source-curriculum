## Summary
A tight, accurate, well-sequenced micro-lesson course: the running example (`acme/rag-api`, an Ollama + ChromaDB + FastAPI "rag-stack") threads cleanly from the first Dockerfile to the final Compose file, and almost every lesson ends in hands-on practice. Before this pass, the biggest opportunities were (1) a few commands that silently fail on the course's own default base image (`python:3.11-slim` ships without `ps` and `curl`), (2) the full-stack walkthrough contradicting the course's own "retry or health-gate your dependencies" advice, and (3) the complete absence of graded projects (`"projects": 0`) — learners never assemble the skills under acceptance criteria. Version pins (Ollama, Chroma, Python packages, model tags) are internally consistent but aging and need an owner decision.

## Depth and coverage gaps
- **No assessed projects.** `course.json` lists `"projects": 0`. Two supplementary projects are drafted (below), mapped to "Write a Dockerfile that packages a Python AI service with lean base images and cache-friendly layers", "Define and operate a multi-service AI stack (LLM, vector store, API/UI) with Docker Compose", and "Apply image-size, config, and sharing best practices that keep an AI Docker workflow reproducible for a team".
- **Few "predict, then run" checks.** Lessons end with practice but rarely ask learners to predict an outcome first. Added "Check your understanding" blocks to lessons 04, 11, 25, and 26, the lessons with the most common misconceptions (container lifetime, cache cascade, what survives `down`, `localhost` inside a container). Supports "Trace what happens between typing docker run and a process starting in a container", "Order Dockerfile instructions so dependency layers are not reinstalled on every code change", "Understand what state persists across a down/up cycle and what does not", and "Explain how Compose services reach each other by service name on a shared network".
- **Non-root containers are never mentioned.** Every image runs as root. A short note in lesson 30 (`USER` instruction, volume ownership pitfalls) would support "Apply image-size, config, and sharing best practices that keep an AI Docker workflow reproducible for a team". Proposed, not applied, because it adds a new concept with bind-mount permission side effects that the owner should decide on.
- **`chromadb` vs. a thin HTTP client.** Lesson 29's `api` installs the full `chromadb` package, which pulls in a large local-database dependency tree even though the API only talks HTTP. The project ships a lighter HTTP-only client package. This would be a strong worked example for "Use multi-stage builds and .dockerignore to keep AI images lean" / image-size practice, but the client package name and version alignment with the 0.5.23 server need verification first.
- **Healthcheck in the final stack.** Lesson 28 teaches `condition: service_healthy`, but lesson 29's capstone file does not use it. Project x02 asks learners to add it, which makes the connection explicit.
- **Measuring "lean."** Lessons 07, 09, and 30 explain size reduction but never set a target. Project x01 gives a concrete size budget and a scripted check.
- **Misconception worth naming in lesson 12:** "`docker push` of a multi-GB image re-uploads everything." The lesson already explains layer de-duplication; a one-line before/after push log would make it concrete.

## Assessment ideas
- **Predict-the-cache item:** show a 7-line Dockerfile and a changed file; the learner marks which steps print `CACHED`.
- **Exit-code matching:** match `Exited (0)`, `Exited (1)`, `Exited (137)` (with `OOMKilled=true` and with `false`) to a cause.
- **Compose-to-flags translation:** given a `docker run` command, write the equivalent service block. Auto-gradable by comparing `docker compose config` output.
- **Survives-`down` sort:** drag 8 items (model cache, `/tmp` file, bind-mounted source, `docker exec pip install`, built image, network, Chroma index, env var) into "survives `down`" / "survives `down --volumes`" / "lost".
- **Rubric for lesson 06 practice:** a 3-level rubric for the "containerize now, later, or not at all" verdict. It scores use of privacy, cost, team-reproduction, and dependency-weight criteria.

## Open questions for the course owner
- **Version pins are aging.** `ollama/ollama:0.5.4`, `chromadb/chroma:0.5.23`, `chromadb==0.5.23`, `ollama==0.3.3`, `torch==2.4.1`, `transformers==4.44.2`, `fastapi==0.115.0`, `uvicorn==0.30.6`, and `llama-cpp-python==0.3.1` were current in late 2024. They are internally consistent, so the course still works if the pinned images remain pullable. Moving Chroma to a newer major line is likely to change the in-container data path (`/chroma/chroma`) and the heartbeat route (`/api/v1/heartbeat`), so upgrades must be made across lessons 23, 26, 29, and 31 together. Please re-verify against current Chroma docs before bumping.
- **Model tags are aging.** `llama3`, `llama3.2`, `llama3.1:8b`, `phi3:mini`, `gemma2:2b`, `mistral`, and `nomic-embed-text` appear throughout. They are probably still pullable but are no longer the newest small models. Decide whether to keep them as stable teaching anchors or refresh them. (Not changed here.)
- **Ollama Python library API.** Newer library versions add `embed()` (returning `embeddings`, plural) next to the `embeddings()` call used in lessons 22 and 29. Verify which form to teach, and pin the library in lesson 22.
- **GPU on macOS.** Lesson 18 states that containers on Docker Desktop for Mac have no Metal GPU access. That is still the general case for ordinary containers. However, Docker has since shipped separate local-model features in Docker Desktop that may run models with host acceleration. Decide whether to mention them as ecosystem context. Their names, availability, and CLI were not verified here.
- **Docker Desktop specifics.** Default memory allocation, the "Settings → Resources" path, the privileged-helper password prompt, and the WSL 2 installer flow (lesson 05) change between releases. Re-verify at the next content refresh.
- **Non-root user.** Should lesson 30 add a `USER` instruction to its best-practices list? It is good practice, but it creates bind-mount UID friction on Linux hosts that the course does not otherwise cover.
- **`course.json` lists 32 lessons, but `sequencing_rationale` says the outline "groups 31 lessons."** The difference is probably the overview. This is a metadata inconsistency to fix in course.json; it was not touched in this pass.
